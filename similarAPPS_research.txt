## 0. Executive Summary

SecureExam should not try to become a literal clone of Examplify, Respondus, or Honorlock in one release. Those products solve different parts of the assessment stack:

- **ExamSoft / Examplify** is strongest as a purpose-built secure assessment delivery platform: a native exam client, offline-first delivery, encrypted answer files, OS lockdown, identity verification, remote-proctoring capture, institutional review, tagging/outcomes, and psychometric reporting.
- **Respondus LockDown Browser + Monitor** is strongest as an LMS-centric secure browser/proctoring layer. It locks down the local client while leaving the LMS/quiz engine as the assessment system of record. It integrates with major LMS platforms and now supports additional camera and monitoring capabilities.
- **Honorlock** is strongest as a SaaS proctoring/security layer tightly integrated with LMSs. Its modern differentiation is hybrid AI + human review, BrowserGuard, device/cell-phone detection, live intervention, analytics, and broad LTI/API integration.

### Strategic conclusion

SecureExam should evolve as a **three-layer assessment platform**:

```text
┌────────────────────────────────────────────────────────────┐
│  INSTITUTION / ADMINISTRATION                              │
│  Tenants • RBAC • Governance • Accreditation • Audit       │
├────────────────────────────────────────────────────────────┤
│  ASSESSMENT CORE                                           │
│  Exams • Question Banks • Tags • Attempts • Grading        │
│  Psychometrics • Results • LMS/LTI Integration             │
├────────────────────────────────────────────────────────────┤
│  TRUST / SECURITY LAYER                                    │
│  Browser controls • Event telemetry • Identity • Proctoring│
│  Offline attempt journal • Integrity scoring • Audit trail │

2. Competitor Benchmark
2.1 ExamSoft / Examplify
Delivery model

Examplify is a native secure exam application rather than merely a browser page. ExamSoft documentation describes secure assessments that can lock down the exam-taker's computer, restrict access to other applications/files/network resources, log activity inside the application, and relaunch in secure mode after a system restart.

Offline operation

ExamSoft's current support documentation confirms that after exam completion Examplify secures, locks, and encrypts answers and attempts to reconnect to upload them. If internet is unavailable, the exam can still be completed and the answer file uploaded later when connectivity returns.

ExamSoft's ExamMonitor materials describe an offline-capable proctoring workflow: audio/video can be recorded during the exam and uploaded after completion.

Design implication for SecureExam: treat the exam attempt as a local transaction log, not a collection of UI state variables.

Recommended model:

Exam Package
   ↓
Encrypted Local Attempt
   ↓
Append-only Answer Events
   ↓
Checkpoint / Hash
   ↓
Finalization
   ↓
Encrypted Upload Queue
   ↓
Server Verification
   ↓
Immutable Attempt Record
Encryption and upload

ExamSoft documentation states that information transmitted to ExamSoft and monitoring data uploaded to its servers are encrypted. It also describes encrypted answer and audio/video files.

SecureExam recommendation:

TLS 1.3 where supported.
Encrypt sensitive attempt artifacts at rest.
Use envelope encryption with a KMS-managed data key.
Never rely on localStorage as the sole storage location for authoritative answers.
Maintain a server-side immutable attempt hash.
Use idempotency keys for uploads.
Keep upload state separate from exam completion state.
Lockdown architecture

Examplify uses a native client with operating-system-level controls. ExamSoft describes scanning system configuration, blocking access to external applications/files/hotkeys/network connections, detecting virtual machines, logging application activity, and relaunching in secure mode.

This is substantially stronger than a normal browser application.

Proctoring

ExamMonitor is primarily a record-and-review workflow, not a conventional always-watching live proctor session. Current ExamSoft documentation says recorded audio/video is analyzed with AI for anomalies and then reviewed by institutional personnel. Incident categories include:

missing applicant
multiple persons
suspicious objects
speaking
off-screen gaze
hand gestures

ExamSoft explicitly cautions that AI flags are not automatically equivalent to cheating; humans determine whether an academic-integrity breach occurred.

Assessment authoring

ExamSoft supports question-bank assessments and tagging of items to outcomes/competencies. Case studies describe tags such as educational outcomes, learning level, course objectives, and accreditation-related categories.

Psychometrics

ExamSoft documentation/case studies expose:

point-biserial correlation
discrimination index
difficulty index
distractor analysis
question-level performance
category/outcome performance

This is a major benchmark for SecureExam.

Governance

ExamSoft supports institutional workflows around exam posting, exam-taker assignment, results release, exam integrity review, and institutional disposition.

3. Respondus LockDown Browser + Monitor
3.1 Architecture

Respondus is fundamentally different from Examplify.

The LMS remains central. LockDown Browser is a locally installed client that launches an LMS assessment in a controlled browser environment.

Current Respondus documentation lists integrations with:

Blackboard Learn
D2L Brightspace
Canvas
Moodle
Sakai
Schoology

Respondus also provides an OEM model that lets assessment vendors embed LockDown Browser capabilities into their own assessment systems.

Security architecture

LockDown Browser is a native installed client, not merely a JavaScript browser script.

This matters because browser JavaScript cannot reliably enforce OS-level guarantees such as:

preventing arbitrary applications from running
preventing task switching
enforcing single-application mode
controlling system-level shortcuts
preventing access to other desktop resources

SecureExam's Phase 1 web product should therefore describe itself as browser-hardened / integrity-monitored, not as an equivalent to a native OS lockdown product.

Reliability

Respondus documentation says LMS auto-save can allow a student to resume after connectivity or browser problems, depending on the LMS.

This is a different reliability model from Examplify:

Examplify:
Local secure exam package → local answer file → upload

Respondus:
LMS quiz engine → browser client → LMS auto-save

SecureExam should combine the best parts:

Local durable attempt journal
+
Server-side checkpoints
+
Offline queue
+
Conflict-safe synchronization
Monitor

Respondus Monitor adds webcam-based proctoring and startup checks. Modern releases also support a second-camera option. In current documentation, instructors can review synchronized video streams including the primary webcam, second camera, and screen recording.

LMS integration

Respondus is deeply LMS-integrated and depends on LTI/external-tool integrations for configuration and launching.

Authoring / question bank

Respondus is not positioned as a complete replacement for every LMS's assessment authoring engine. Its Respondus 4.0 ecosystem supports importing/exporting assessment content and question-bank workflows.

A legacy CSV specification exposes fields such as:

8. Code Audit Checklist
8.1 Multi-tenant isolation

Verify every tenant-owned entity has an explicit tenant boundary.

Preferred pattern:

model Tenant {
  id        String   @id @default(cuid())
  name      String
  createdAt DateTime @default(now())

  users     User[]
  exams     Exam[]
  questions Question[]
}

model Exam {
  id        String @id @default(cuid())
  tenantId  String
  tenant    Tenant @relation(fields: [tenantId], references: [id])

  title     String
  status    ExamStatus
}

Then enforce tenant scoping at the service/repository layer.

Do NOT rely on the UI to prevent cross-tenant access.

Required tests
Student from Tenant A cannot read Tenant B exam.
Instructor from Tenant A cannot mutate Tenant B question bank.
Admin from Tenant A cannot access Tenant B audit logs.
Attempt IDs cannot be used as an authorization bypass.
File/object storage keys contain tenant isolation.

11. Offline Exam Architecture
Do not use localStorage for authoritative exam answers

localStorage is useful for small preferences and non-sensitive UI state.

For exam answers use:

IndexedDB

Recommended local structure:

SecureExamDB
├── examPackage
├── attempt
├── answers
├── events
├── syncQueue
├── mediaManifest
└── checkpoints

Each answer mutation becomes an event:

{
  "attemptId": "A123",
  "questionId": "Q77",
  "sequence": 1042,
  "answer": "...",
  "clientTimestamp": "...",
  "previousHash": "...",
  "hash": "..."
}

The server can reconstruct the attempt.

This is substantially more resilient than repeatedly overwriting a JSON object.

12. Synchronization Strategy

Use an idempotent append-and-ack protocol.

Client:

POST /attempts/:id/events
Idempotency-Key: attemptId:clientSequence

Server:

Validate authentication.
Validate tenant.
Validate attempt state.
Validate sequence.
Store event.
Verify hash chain.
ACK sequence.
Update materialized attempt state.

Client then removes acknowledged events from the pending queue.

Conflict handling

Do not use naive last-write-wins for answers.

Instead:

Attempt
 ├── event sequence 100
 ├── event sequence 101
 ├── event sequence 102
 └── ...

The sequence is authoritative.

24. Native Client Trust Model

Use a zero-trust assumption:

Client is potentially compromised.
        ↓
Server validates all claims.
        ↓
Client provides telemetry/evidence.
        ↓
Risk engine evaluates evidence.

This prevents SecureExam from turning into a "security theater" application where the UI says "secure" while the server has no verifiable evidence.

34. Security Principles
Server authoritative.
Client untrusted.
Tenant isolation everywhere.
Least privilege.
Immutable audit trail.
Encryption in transit and at rest.
Key management separated from application code.
No secrets in browser bundles.
No sensitive answers in ordinary browser storage unless encrypted and explicitly justified.
Idempotent synchronization.
Version all exam content.
Never treat an AI flag as a disciplinary verdict.
Preserve evidence needed for institutional review.
Design accessibility and accommodations as first-class features.
Maintain explicit data retention/deletion policies.

37. Bottom-Line Recommendation

The fastest route to a serious SecureExam product is:

Do not start by trying to beat Examplify at OS lockdown.

First beat it at:

customization,
reliability,
assessment architecture,
question-bank intelligence,
institutional governance,
interoperability,
transparent integrity workflows.

Then build the native Windows client once the web/cloud assessment core is mature.

The architectural insight from the benchmark is simple:

Exam security is not one feature. It is a chain of trust.

Identity
   ↓
Authorized Exam
   ↓
Trusted Attempt
   ↓
Durable Answers
   ↓
Verifiable Events
   ↓
Secure Submission
   ↓
Human-Reviewable Integrity Evidence
   ↓
Defensible Grade

If any link is weak, the system is weak.

SecureExam should therefore be engineered as an assessment integrity platform, not merely an online quiz application with a fullscreen button.
